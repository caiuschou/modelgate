# 团队与成员交互规格

**版本:** 1.0  
**日期:** 2026年4月  
**文档类型:** 交互设计规格（后续里程碑）

> **实现范围：** 本文描述 **组织协作** 能力的前端交互与信息架构，**不包含在当前 v1 产品契约内**。单账户边界与「不做团队」的约定见 [产品范围与原则](../../product/product-scope-principles.md)。功能级验收目标见 [功能详解 — 3.2 组织与成员](../../product/features.md#32-组织与成员团队--多用户协作)。**服务端分期、迁移与路由落地**见 [团队与成员开发方案](../../development/teams-and-members-implementation.md)。

---

## 一、设计目标

- **上下文清晰：** 用户始终能识别「当前正在操作哪个团队」；跨团队资源不错配。
- **邀请可控：** 邀请链路短、权限明确；过期与重复邀请有可读反馈。
- **权限诚实：** 无权限的菜单与按钮不展示或可点状态明确禁用（优先隐藏次要入口），避免误导。
- **危险可恢复：** 移除成员、移交所有权、删除团队等操作需二次确认，关键文案说明后果。

---

## 二、术语

| 术语 | 说明 |
|------|------|
| 团队（Team） | 资源共享与治理边界；拥有名称、可选唯一 slug、成员列表与角色。 |
| 成员（Member） | 某一 `User` 在某 `Team` 中的参与关系，含角色。 |
| 当前团队 | 本会话（或 URL）中选中的团队；列表页、统计、密钥等均默认按当前团队过滤。 |
| 个人账号 | 登录主体；可属于多个团队，全局设置（密码、偏好）与团队无关。 |
| 邀请 | 通过邮件链接或站内令牌将**已有或新建**用户纳入团队并赋予初始角色。 |

## 三、信息架构

### 3.1 全局：团队上下文切换器

**位置（建议）：** 侧栏顶沿 Logo 下方，或顶栏左侧（名称 + Chevron）。

**展示：**

- 当前团队名称（过长截断 + Tooltip 全称）。
- 下拉列出用户所属全部团队；每项显示名称 + 可选 slug。
- 底部分割线：**创建团队**（有权限时）、**团队管理**（跳转当前团队设置，或等价入口）。

**交互：**

| 操作 | 行为 |
|------|------|
| 选择另一团队 | 切换上下文：导航到该团队默认落地页（建议 `/` 或 `/teams/:teamId`）；列表类页面重置筛选为团队默认。 |
| 仅有一个团队 | 仍可显示团队名，下拉仅一项 + 创建入口（若允许）。 |
- **可访问性：** 切换器为 `combobox` 或带 `aria-haspopup="listbox"` 的按钮；列表项 `role="option"`。

### 3.2 导航项与团队的关系

引入团队后，下列模块的默认语义为 **当前团队范围内**（与 [导航设计](navigation.md) 并存时，需在导航文档中增补说明）：

| 模块 | 团队语境下的含义 |
|------|------------------|
| API 密钥 | 列出/创建属于 **当前团队** 的密钥（个人密钥若保留，需单独 Tab 或筛选，见 7.3）。 |
| 日志中心 | 默认展示当前团队审计；保留按 Key/模型等筛选。 |
| 统计分析 | 聚合当前团队用量（跨团队汇总可在平台级报表另页，本文不强制）。 |
| 渠道管理 | 若渠道为实例级配置，可仍为全局；若为团队级，则随团队切换。 **落地时与后端资源模型一致。** |

## 四、路由与页面

路径为建议形态，实现时可带 `slug` 或短 id，但须稳定、可分享书签。

| 路径 | 说明 | 访问 |
|------|------|------|
| `/teams` | 若用户多团队：卡片或表格列表；单团队可重定向到该团队首页。 | 已登录 |
| `/teams/new` | 创建团队向导或单页表单。 | 已登录，且策略允许自建团队 |
| `/teams/:teamId` | 团队概览（用量摘要、成员数量、最近动态占位）。 | 须为该团队成员 |
| `/teams/:teamId/settings` | 团队一般设置：名称、slug、删除团队等。 | Owner / Admin（删除仅 Owner） |
| `/teams/:teamId/members` | 成员列表与管理主页面。 | 成员；管理操作依角色 |
| `/teams/:teamId/invitations` | 待处理邀请列表（可选；亦可合并到 members 页的 Tab）。 | Admin+ |
| `/invite/:token` | 接受邀请落地页（登录后校验 token）。 | 公开落地，操作需登录 |

**深度链接：** 分享 `/invite/:token`；不要在 URL 中放敏感信息。

## 五、核心流程

### 5.1 创建团队

1. 用户点击 **创建团队**。
2. 表单字段：**团队名称**（必填）、**Slug**（可选，唯一性校验，格式提示如小写连字符）。
3. 提交成功：用户自动成为 **Owner**；切换当前团队为新团队；Toast 成功 + 进入团队概览或引导「邀请成员」。

**错误：** 名称/slug 冲突、网络失败；保留表单内容（slug 冲突时聚焦 slug 字段）。

### 5.2 邀请成员

**入口：** `成员` 页主按钮 **邀请成员**（Admin 及以上可见）。

**步骤（建议对话框或侧栏，2 步内完成）：**

1. 输入 **标识**：邮箱（优先）或用户名（若产品支持按用户名邀请）。支持逗号分隔批量（可选）。
2. 选择 **角色**：Member（默认）/ Admin；Owner 不可通过邀请直接赋予（须移交，见 5.5）。
3. 提交 → 展示 **结果摘要**：成功发送数、已已是成员数、失败原因分行列表。

**邀请链接模式（可选）：** 「复制邀请链接」生成带 `token` 的 URL；需展示 **过期时间** 与 **一键撤销**（签发者优先）。

**邮件 / 通知：** 文案包含团队名、邀请人、角色、按钮链到 `/invite/:token`。

### 5.3 接受邀请

1. 未登录：落地页说明团队名与角色 → **登录** / **注册**（注册后仍绑定同一 token）。
2. 已登录：校验 token → 成功则加入团队 → Toast → **切换到此团队** 或询问用户是否切换。
3. **失败态：** token 无效、过期、团队已删、邮箱不匹配（若策略要求）— 单一友好说明 + 返回首页或联系邀请人。

### 5.4 成员列表（`/teams/:teamId/members`）

**表格列（建议）：**

- 成员显示名 / 用户名  
- 邮箱（若有且当前用户有权查看）  
- 角色（Badge）  
- 加入时间  
- 操作：`更改角色`、`移除`（依权限）

**排序 / 搜索：** 按名称搜索；按角色筛选。

**空状态：** 「尚无其他成员」+ **邀请成员** 主按钮。

**行级操作：**

| 操作 | 触发 | 确认 |
|------|------|------|
| 更改角色 | 行菜单或内联下拉 | 若提升为 Admin，可用轻量确认 |
| 移除 | 危险按钮样式 | Dialog：不可撤销说明；提交后该行消失 |

**约束交互：**

- **不能移除唯一 Owner**；移除前须先移交（见 5.5）。
- **不能修改自己的角色**为低于当前会话所需最低权限而导致把自己锁死（实现侧校验 + 前端禁用自降权若会违例）。

### 5.5 移交团队所有权

**入口：** 团队设置 → **危险区域** 或成员行（原 Owner）。

**流程：**

1. 选择新 Owner（仅 Admin 或 Member 列表中的其他成员）。
2. 强校验：输入团队名或 `TRANSFER` 确认词。
3. 成功后：原 Owner 降为 Admin（默认策略）或 Member — **产品需固定一种并在 UI 写明**；新 Owner 单一来源展示。

### 5.6 离开团队

**入口：** 成员页自己所在行，或团队设置底部。

**规则：**

- Owner **不可直接离开**；须先移交或删除团队。
- 其他角色：确认 Dialog → 离开成功 → 切换到下一可用团队或个人上下文；若无团队，落到 `/teams` 或新建引导页。

### 5.7 删除团队

**入口：** 团队设置 → 危险区域，仅 Owner。

**流程：** 输入团队名确认 → 删除 → 不可恢复说明。成功后清除上下文缓存、重定向到 `/teams` 或剩余默认团队。

## 六、角色与界面权限（摘要）

以下控制 **导航与按钮显隐**；细粒度 API 权限由后端权威决定。

| 能力 | Owner | Admin | Member |
|------|:-----:|:-----:|:------:|
| 查看团队概览与成员列表 | ✅ | ✅ | ✅ |
| 邀请成员 / 撤销邀请 | ✅ | ✅ | ❌ |
| 更改他人角色（非 Owner 赋值） | ✅ | ✅ | ❌ |
| 移除成员 | ✅ | ✅ | ❌ |
| 编辑团队名称 / slug | ✅ | ✅ | ❌ |
| 移交所有权 | ✅ | ❌ | ❌ |
| 删除团队 | ✅ | ❌ | ❌ |
| 离开团队 | 须先移交 | ✅ | ✅ |

## 七、与个人资源共存（可选策略）

若 v1.5+ 保留「个人 API 密钥」：

- **团队切换器** 增加 **个人** pseudo-context：选择后密钥与日志仅展示 `user` 级、无 `team_id` 的资源。
- 创建密钥时询问归属：**当前团队** 或 **仅个人**（默认随当前上下文）。

若产品决定 **全部团队化**，则无个人 pseudo-context，文档删除本节约束。

## 八、状态、反馈与文案原则

| 场景 | 交互 |
|------|------|
| 切换团队 | 全局 loading skeleton ≤ 300ms 感知；长请求显示进度或顶栏进度条。 |
| 邀请已发送 | Toast「邀请已发送至 xxx」 |
| 已是成员 | 内联提示，不当作错误惊扰 |
| 权限不足 | 403 页面或空态：「你没有权限查看该团队」+ 返回 |
| 团队被删 | 若当前上下文失效，Banner + 强制切换 |

**文案：** 使用「团队 / 成员 / 邀请」，避免与「租户」混用；错误信息不泄露其他团队存在性（404 统一表述）。

## 九、无障碍与安全

- 表格：`table` + `th` scope；操作按钮 `aria-label` 含成员名。
- Dialog：焦点陷阱、Esc 关闭、标题 `aria-labelledby`。
- 邀请链接：不在客户端长期存储明文 token；复制操作给予成功反馈。

## 十、API 契约（供后端联调草案）

以下为逻辑资源，路径可按现有 API 风格调整：

- `GET /teams` — 当前用户所属团队  
- `POST /teams` — 创建（body: `name`, `slug?`）  
- `GET /teams/:id` / `PATCH /teams/:id` / `DELETE /teams/:id`  
- `GET /teams/:id/members`  
- `PATCH /teams/:id/members/:userId` — `role`  
- `DELETE /teams/:id/members/:userId`  
- `POST /teams/:id/invitations` — `email | username`, `role`  
- `DELETE /invitations/:id`  
- `POST /invitations/:token/accept`  

错误码与 [功能详解 — API 请求处理](../../product/features.md#五api-请求处理) 保持一致性；跨团队越权一律 **404 或 403** 由安全策略统一。

## 十一、与测试的约定

- E2E：使用 Playwright 可访问定位（`getByRole` / `getByLabel`）；团队名与邀请 token 使用时间戳或 UUID 避免冲突。
- 覆盖：创建团队 → 邀请 → 接受 → 改角色 → 移除；Owner 移交与删除团队的负面路径各至少一条。
