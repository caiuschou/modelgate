# ModelGate 充值与 LLM 调用扣费 — 产品方案

**版本:** 1.2  
**更新日期:** 2026年4月  
**文档类型:** 产品方案（PRD 级）

> **与代码的关系：** 本文描述**目标态**业务能力与规则。实现进度以 [实现状态](../implementation-status.md) 为准；与 [功能详解](features.md) 第七章「计费规则」、[产品路线图](roadmap.md) 中的「充值中心」一致时，以本文对流程与数据模型的展开为准。  
> **v1 范围契约：** 资源与账务边界以**注册用户**为单位，与 [产品范围与原则](product-scope-principles.md) 一致；不包含团队/组织级资金池划拨（可作为后续里程碑）。  
> **计价货币：** 账户余额、充值、扣费、流水与价格表均以 **美元（USD）** 为记账与展示货币；用户支付时若经渠道以其它货币结算，入账按**支付成功时约定的汇率折 USD** 记入余额（具体汇率来源与舍入规则由支付集成方案定义）。

**用语：** **API 密钥** = 访问网关的凭证；**Token** = 模型用量单位（输入/输出计费）；**余额** = 用户预付资金对应的可用额度，**以 USD 计**（可与内部「点数」1:1 锚定 USD，对外文案需统一）。  
**交互规格：** 控制台布局、Tab、充值与流水页面的交互与验收清单见 [充值与计费 — UI/交互规格](../design/interaction/recharge-and-billing.md)。

## 一、背景与目标

### 1.1 背景

ModelGate 作为 LLM 统一接入网关，需要在「可控成本」前提下向终端用户提供可调用的模型能力。预付费（先充值、后使用）可降低坏账风险，并与按量计费（通常以 Token 为计量基础）天然契合。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| **商业闭环** | 用户可充值、系统可按调用扣费，形成可追溯账务流水。 |
| **计量透明** | 扣费可解释到「模型、用量维度、单次请求」。 |
| **体验可控** | 余额不足时行为明确（拒绝或提示），错误码与控制台引导一致。 |
| **可运营** | 支持对账、争议追溯；为后续活动赠送、阶梯价等扩展留接口。 |

### 1.3 非目标（本文不展开）

- 具体支付渠道对接细节（如 Stripe、PayPal、银行卡及本地钱包等）的接口字段与回调验签（由支付集成专项文档描述）。  
- 税务、发票或销售凭证（invoice/receipt）的完整财务合规方案（仅列产品规则要点）。  
- 多租户组织账户间的余额调拨（后续里程碑）。

## 二、范围与角色

### 2.1 范围

- **账户侧：** 充值入账、余额展示、消费扣减、流水查询、余额不足策略。  
- **调用侧：** Chat/Completion 等产生模型用量的请求在完成或结算点后扣费（含流式场景的结算规则）。  
- **控制台：** 充值入口、账单/流水列表、与 [导航设计](../design/interaction/navigation.md) 中「充值中心」一致的信息架构。

### 2.2 角色

| 角色 | 职责 |
|------|------|
| 注册用户 | 充值、查看余额与流水、处理余额不足时的充值引导。 |
| 系统 | 计量、计价、扣费、幂等与并发控制、审计记录。 |
| 运营/财务（后续） | 对账报表、退款审批、价格配置。 |

## 三、用户故事（摘要）

```
作为 注册用户
我想要 向账户充值并获得可用余额
以便于 持续调用模型而无需每次单独签约

作为 注册用户
我想要 在控制台看到每次调用扣了多少美元、剩余多少余额
以便于 控制成本并核对账单

作为 系统集成方
我想要 在余额不足时收到明确、稳定的错误码与提示
以便于 在应用中引导用户充值或切换账户
```

## 四、核心概念与账户模型

### 4.1 余额（钱包）

- 用户维度的**可用余额**，以 **USD** 为唯一记账单位，或与之 1:1 锚定的内部「点数」（与 USD 等价）；产品对外文案需统一为美元金额或明确标注 USD。  
- **增加：** 主要来自充值成功入账；后续可扩展赠送、补偿入账。  
- **减少：** 来自按调用确认的扣费；退款、调账为后续能力。

### 4.2 现金余额与赠送金（可选分期）

| 类型 | 说明 |
|------|------|
| **现金余额** | 用户支付充值获得，可对应开票规则。 |
| **赠送金** | 活动发放，可与现金分账；可配置**不可开票**、**优先消耗**、**有效期**。 |

**MVP 建议：** 仅维护**单一可用余额**字段，不区分赠送；规则在文档中预留。

### 4.3 预扣 / 冻结（可选进阶）

针对**流式响应**或**长耗时请求**，可采用：请求开始时**冻结**预估费用上限，结束时按实际上传入/输出用量**结算**并解冻差额，降低透支与纠纷。

**MVP 建议：** 不实现冻结，仅在**调用完成且可取得用量**后扣费；余额不足时的处理见第六节。

### 4.4 与 API 密钥、配额的关系

- **余额：** 资金是否足够支付本次用量。  
- **配额（quota）：** 可为每日/每月 Token 上限、请求次数等（见 [功能详解](features.md)）。  

校验顺序建议：**认证 → 配额 → 余额（及预估）→ 上游调用 → 计量扣费**。二者同时生效时，错误原因应可区分（配额耗尽 vs 余额不足）。

## 五、计价与扣费规则

### 5.1 计量依据

- **首选：** 上游或网关聚合后的 **usage**（如 `prompt_tokens`、`completion_tokens`）。  
- **兜底：** 若无法取得精确 usage，采用**经公示的估算规则**（如按字符/ tokenizer 估算），并在账单中标注「估算」；具体算法由技术方案定义。

### 5.2 价格表

- 按 **模型 ID**（及可选：渠道）配置单价，例如：  
  - 输入：USD / 百万 Token（prompt）  
  - 输出：USD / 百万 Token（completion）  
- 支持后续扩展：活动价、阶梯价、会员折扣（不在 MVP 强制）。

### 5.3 扣费时机

| 场景 | 扣费时机 |
|------|----------|
| 非流式同步请求 | 响应成功返回且取得 usage 后，一次性扣费。 |
| 流式（SSE 等） | 流结束或连接关闭后，汇总 usage 扣费；若中途失败，按已产生 usage 或产品规定的**最小计费单位**扣费（需在用户协议/文档中固定）。 |

### 5.4 调用失败是否扣费

| 情形 | 建议规则 |
|------|----------|
| 上游 4xx（参数错误等） | 一般不扣费（无有效用量或约定为 0）。 |
| 上游 5xx / 超时 / 网关未拿到响应 | 默认**不扣费**或仅扣**最小计量**；一旦采用「可扣最小量」，须产品公示。 |
| 流式中断 | 按已输出 token 计费的，按实际 usage 扣费；需在文档说明。 |

## 六、业务流程

### 6.1 充值流程（概要）

1. 用户在控制台选择金额或档位 → 发起支付。  
2. 支付渠道异步通知支付成功（**幂等键**：商户订单号或等价 id）。  
3. 服务端校验签名与金额 → **入账**：增加余额，写入**充值流水**（时间、金额、渠道、外部单号、用户 id）。  
4. 用户侧展示「到账成功」与更新后余额。

**规则对齐 [功能详解](features.md)：** 最低充值金额、到账实时性等以产品配置为准；若该章仍以人民币举例，**数值与货币以运营在系统中的 USD 配置及本文为准**（例如最低充值可配置为 **$10 USD**）。

### 6.2 调用与扣费流程（概要）

1. 请求进入网关：鉴权、配额检查。  
2. **余额检查：** 若策略为「必须先有正余额」，则余额 ≤ 0 时直接返回错误（见 7.2）。若采用「预估预扣」，则检查可用余额是否覆盖预估上限。  
3. 转发上游，获取响应与 usage。  
4. 计算本次费用 → **扣减余额** → 写入**消费流水**（关联 `request_id` / 审计 id、`api_key_id`、`model`、输入/输出 token、金额、时间）。  
5. 若扣费失败（并发导致余额不足等），需定义**补偿策略**（如记欠款、禁止下次请求直至补齐），MVP 可采用**强一致扣费 + 失败则回滚调用状态**或与产品约定「仅允许扣费成功才算调用成功」二选一，由技术方案定稿。

### 6.3 余额不足策略

| 策略 | 说明 |
|------|------|
| **硬阻断** | 余额不足以支付本次实际费用时，返回统一错误，本次调用不计成功业务结果（若上游已产生费用，须与 5.4 失败规则一致，避免逻辑冲突）。 |
| **仅告警** | 允许负数（后付费体验）；MVP 不推荐，与「预付费」定位不一致。 |

推荐 **预付费 + 硬阻断**，与 [功能详解](features.md)「余额不足停服」一致。

## 七、产品与接口要点

### 7.1 控制台

- **充值中心：** 充值入口、档位/自定义金额（**USD**）、支付方式、**充值记录**。  
- **账单 / 流水：** 消费明细列表、按时间/模型筛选、导出（CSV，分期）；金额列统一为 **USD**，展示精度（如小数点后 2 位）由前后端约定。  
- **仪表盘：** 当前余额（USD）、近期消费趋势（与 [统计分析页方案](../design/interaction/analytics.md) 联动）。  

### 7.2 API 错误与文档对齐

与 [产品 API 文档](api.md) 中错误码体系对齐，例如：

- `quota_exceeded`：配额类不足。  
- **余额类：** 建议独立错误码（如 `insufficient_balance`）或 HTTP **402**（若团队约定统一使用），响应体包含 `message`、可选 `balance`、`required_minimum`（均为 **USD**），可选 `currency: "USD"`，便于客户端引导充值。

### 7.3 与审计日志

每次扣费流水宜与 [审计日志](audit-log.md) 中的请求 id 关联，便于「一次请求 ↔ 一笔扣费」对账。

## 八、风控与账务安全

| 维度 | 要求 |
|------|------|
| **幂等** | 充值回调、重复通知不重复入账；扣费重试不重复减款。 |
| **并发** | 多请求同时消耗同一余额时，采用行级锁、乐观锁或余额版本号，防止透支。 |
| **审计** | 所有余额变动可追溯；敏感操作留痕。 |
| **对账** | 日切对账：支付渠道入账总额 vs 系统充值流水；消费汇总 vs 上游用量（若可获取）。 |

## 九、退款与凭证（规则层）

与 [功能详解](features.md) 第七章对齐要点（货币与门槛以 **USD 政策** 为准）：

- 未使用余额可申请退款（流程、审核、周期由运营政策决定；退款币种一般为 **USD** 或与原支付路径一致，以渠道能力为准）。  
- 手续费与周期（如文档中的 5%、3–5 个工作日）以正式发布政策为准。  
- 发票或 **invoice/receipt** 一般针对**充值实付（USD）**；消费为余额消耗，不再重复开具（除非税务另有要求）。

## 十一、验收标准（摘要）

- 用户可完成至少一种支付路径的充值，余额与充值记录正确。  
- 发起一次可返回 usage 的模型调用后，余额减少，消费流水与请求可追溯关联。  
- 余额为 0 或不足以支付本次费用时，行为符合第六节、第七节约定，且错误码稳定。  
- 并发压测下不出现负余额（在「不允许透支」前提下）。
