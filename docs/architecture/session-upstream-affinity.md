# 会话级上游亲和（多上游 / 同会话固定线路）

**版本:** 1.2  
**编写日期:** 2026年4月17日  
**文档类型:** 产品与架构设计 + 控制台交互规格（规划）  
**适用范围:** 网关 API Key 背后允许多个上游时，保证 **同一会话** 内多次请求使用 **同一条上游线路**，且不依赖每请求切换 BYOK 的请求头；本文同时描述 **用户控制台** 的配置交互。

> **落地状态：** 网关侧 **`POST /v1/chat/completions`** 已实现会话键、`upstream_pool` 与 `session_upstream_bindings` 的 Round Robin + 绑定（见 `src/session_upstream.rs`、`resolve_chat_upstream`）；控制台 **`/api-keys/:id`** 已提供 §7 所述配置卡片。细节以 [开发 API](../development/api.md) 与 [实现状态](../implementation-status.md) 为准。

---

## 1. 概述

### 1.1 目标

- **一把网关 Key** 在配置上可对应 **多个上游候选**（例如实例 `[upstream]`、多个 BYOK profile，或未来扩展的多线路池）。
- 属于 **同一会话（session）** 的连续请求（例如同一条多轮对话）应 **始终路由到同一上游**，避免上下文、计费或供应商侧状态因换线而割裂。
- **不新增** 专门用于「选上游」的 HTTP 头；会话标识复用 **已有约定**（见 §2）。
- 本设计在 **路由语义** 上 **不采用** `X-MG-Byok-Id`：不在每次请求通过该头显式指定 BYOK；上游由 **Key/空间配置 + 会话键** 共同决定（实现时可保留该头用于其它兼容场景，但 **不作为本会话亲和方案的一部分**）。

### 1.2 与现有概念的关系

| 概念 | 说明 |
|------|------|
| **网关 API Key** | `Authorization: Bearer`；标识调用方与策略（配额、白名单等）。 |
| **上游候选** | 平台 `[upstream]`、或解密后的 BYOK `base_url` + 供应商密钥等；具体列表由产品与数据模型定义。 |
| **会话键（session key）** | 用于在多次请求间识别「同一会话」的稳定字符串；来源见 §2。 |
| **亲和（affinity）** | 给定 `(api_key_id, session_key)`，在允许的上游集合上映射到 **唯一确定** 的一项；**推荐** 首次用 Round Robin 选定并 **落库绑定**（见 §4.1）。 |

### 1.3 设计原则

- **会话键来源明确：** 只接受文档约定的头字段或 JSON 字段，避免隐式猜测。
- **租户隔离：** 亲和计算必须包含 **网关 Key**（或 `user_id` + `team_id` 等与鉴权一致的主键），避免跨 Key 串线。
- **可观测：** 审计中可记录最终选用的上游标识（如 `byok_profile_id` 或等价 id），便于与现有日志、计费对齐。
- **与 BYOK 安全模型一致：** 解密与归属校验仍遵循 [BYOK 设计](./byok-design.md)；本会话方案只解决 **在多个合法上游中选哪一个**。

## 2. 会话键（不新增 Header）

以下 **二选一**（产品需固定优先级与回退行为，避免同一请求两者皆有时冲突）。

### 2.1 推荐：`X-Thread-Id`

- **已有** 请求头：`X-Thread-Id`（见 [开发 API](../development/api.md) 可选头说明）。
- 与审计、日志中心中的 **thread / 会话** 维度一致；客户端在同一会话中应发送 **相同非空** 值。
- **不引入** 新的 ModelGate 专用头。

### 2.2 备选：请求体中的 `user`（OpenAI Chat Completions 兼容）

- 当 **不能使用任何可选头**（除 `Authorization`）时，使用 JSON body 中的 `user` 字段（字符串）作为会话键。
- 要求客户端为同一会话提供 **稳定相同** 的 `user`；网关需解析 body（与现有 model / stream 解析同路径），并定义 **缺失 `user` 时的行为**（例如仅走 Key 默认单上游、或拒绝请求）。

### 2.3 无会话键时的行为（建议）

若既无有效 `X-Thread-Id` 又无有效 `user`（按产品选定优先级判断为空）：

- **方案 A：** 退化为 **Key 级默认上游**（例如单一默认 BYOK 或平台上游），无会话级亲和。
- **方案 B：** 返回 **400**，提示必须提供会话标识（对强依赖亲和的部署适用）。

## 3. 多上游集合（配置侧）

逻辑上需满足：

- 每个网关 Key（或团队策略）关联 **有序的上游候选列表**（含平台线路与/或若干 BYOK profile id）；列表 **顺序** 在 **Round Robin** 中具有语义（见 §4.1）。
- 集合变更与已绑定会话的关系：有状态绑定下，**已落库的会话** 可继续指向原上游，直至 TTL 或清理策略失效；**新会话** 使用当前池与当前 RR 游标。

**控制台如何编辑该列表、开关与保存流程：** 见 §7。

## 4. 亲和算法

### 4.1 推荐：Round Robin 首次选路 + 数据库绑定

**适用：** 需要 **严格**「首次选定后同会话不变」，且希望在 **上游池变更** 后仍尽量保留旧会话线路时使用。

**流程：**

1. 以 `(gateway_api_key_id, normalized_session_key)` 查 **绑定表**。  
2. **命中：** 使用已记录的上游（解密 BYOK 等流程不变）。  
3. **未命中（新会话）：**  
   - 在 **当前 Key** 的上游池上执行 **Round Robin**：根据 **持久化游标**（建议 **每个 `api_key_id` 独立**）选取池内 **下一项** 作为本会话上游；  
   - **原子地**：游标前进（`mod N`）、写入绑定表 `(api_key_id, session_key) → upstream_ref`；  
   - 再转发请求。

**Round Robin 游标：**

- 存于数据库单行或专用表字段（例如「下一新会话从第 `k` 项开始」），与 **上游池版本** 可一并考虑，避免池编辑与并发 RR 错乱。  
- **并发：** 对同一 `session_key` 的首次并发请求，依赖 **`UNIQUE(api_key_id, session_key)`** 与事务，保证只绑定一次；游标推进应在 **选定上游的同一事务** 内完成，避免双会话抢到同一游标位置导致不一致。

**特点：** 已绑定会话在上游池 **删除/重排** 后仍可保持稳定（直至策略清理）。  
**代价：** 持久化、过期策略、多实例下需 **同一数据库** 或等价分布式锁/事务（与当前 SQLite/单实例部署可先行，扩展时再议）。

### 4.2 备选：无状态哈希

对规范化后的 `session_key` 与 `api_key_id` 计算：

`index = hash(f(api_key_id, session_key)) mod N`

其中 `N` 为当前候选集合大小，在 `N` 固定且集合 **仅追加** 时，同一会话通常稳定映射到同一槽位。

**特点：** 无需绑定表与游标。  
**风险：** **删除或重排** 上游会改变 `N` 或槽位含义，可能导致 **同一会话换上游**。缓解方式包括：对集合做 **版本号**、仅允许 **追加**、或迁移期双读旧映射。

---

## 5. 显式排除：`X-MG-Byok-Id`

本会话亲和方案 **不要求、也不依赖** 客户端在每次请求携带 `X-MG-Byok-Id` 来选择上游。  
路由决策应基于 **§2 会话键** + **§4 亲和算法** + **Key/实例配置**。

> 若运行时仍暴露 `X-MG-Byok-Id`，需在产品上定义其与亲和的优先级（例如 **亲和优先** 或 **显式头优先**）；本规格推荐以 **会话亲和 + Key 配置** 为唯一选路来源，避免双重语义。

## 6. 与当前代码的对应关系

- Chat 入口：`src/handlers/proxy.rs` 中 `chat_completions` 将 `thread_id` 与 body 解析为 `session_key`（`session_upstream::parse_session_key`），传入 `resolve_chat_upstream`。
- 选路：`resolve_chat_upstream` 在平台强制头之后、传统 `X-MG-Byok-Id` / 默认 BYOK 之前，尝试会话亲和（`session_upstream::pick_session_upstream`）。

## 7. 控制台配置与交互（规划）

为 **会话级上游亲和** 提供控制台侧的 **信息架构、表单字段、校验与文案**，与网关行为一致，避免用户误解「默认上游」与「会话池」的关系。

> **落地状态：** 控制台 **尚未** 提供本节所述区块；当前 `/api-keys/:id` 仅有「默认 Chat 上游」等与 [BYOK 设计](./byok-design.md) 相关的配置。

### 7.1 入口与导航

| 项目 | 建议 |
|------|------|
| **URL** | `/api-keys/:id`（密钥详情页），在现有「默认 Chat 上游」卡片 **下方** 或 **并列** 新增独立卡片，避免单屏过长时可折叠。 |
| **面包屑** | 与 [API 密钥能力增强 — 五、页面信息架构](../product/api-key-capability-enhancement.md#五页面信息架构与导航) 一致：`首页 > API 密钥 > {名称}`。 |
| **权限** | 与编辑该 Key 的权限一致；已吊销 Key：整块只读或隐藏（与详情页只读规则一致）。 |

### 7.2 区块：「会话上游（亲和）」

#### 标题与说明

- **标题：** `会话上游` 或 `多上游与会话固定线路`（二选一，产品定稿）。
- **说明文案（建议）：**  
  「开启后，同一 **会话**（见下方会话键）内的多次请求会固定使用 **同一条** 上游线路。**新会话** 首次请求时，在下列 **上游池** 中按 **顺序轮流（Round Robin）** 分配一条线路，并在服务端 **记录绑定**；之后同一会话始终走已绑定线路。」
- **帮助链接：** 指向 [开发 API](../development/api.md) 中 `X-Thread-Id` / 可选 body `user` 的说明。

#### 主开关

| 控件 | 说明 |
|------|------|
| **启用会话亲和** | 开关（Switch）。关闭时：网关不创建新绑定，行为退化为产品定义的 **单默认上游**（与现有 Key 默认 BYOK / 平台上游一致，见 §2.3）。 |
| **依赖** | 启用前需至少 **一个** 上游候选（见下文「上游池」）；若列表为空，开关 **禁用**，辅助文案：「请先配置上游池（至少一项）。」 |

#### 上游池（有序列表）

- **含义：** 列表 **顺序** 即 **Round Robin 顺序**：第 1 个新会话分配到池内第 1 项，第 2 个新会话到第 2 项，至末尾后回到第 1 项（游标在服务端按 Key 维度维护，见 §4.1）。
- **每一项可选类型（建议）：**  
  - **平台上游**（`[upstream]`）；  
  - **指定 BYOK**（从当前个人/团队上下文中可选的 `byok_profiles` 条目选取，已吊销项不可选）。
- **操作：** 添加行、删除行、**拖拽排序**（桌面）或「上移 / 下移」按钮（保证无拖拽时的可访问性）。
- **校验：** 同一池内 **不允许** 重复选择同一 BYOK id；平台线路至多一条（若产品允许多条平台类候选，需单独定义，默认 **一条**）。
- **空池：** 不允许保存；提示「至少添加一条上游」。

#### 会话键策略（与网关一致）

| 选项 | 说明 |
|------|------|
| **优先使用 `X-Thread-Id`** | 默认推荐；非空则以其为会话键。 |
| **否则使用 body `user`** | 当未传 `X-Thread-Id` 或为空时，使用 Chat Completions JSON 的 `user` 字段。 |
| **两者皆空时** | 与 §2.3 一致：退化为单默认上游 **或** 报错；控制台应用 **单选** 展示网关实际策略（与后端配置一致，避免 UI 与 400 不一致）。 |

#### 只读信息（可选，Phase 2）

- **当前 Round Robin 游标位置**（展示为「下一新会话将使用：池内第 *n* 项」）— 仅运维排障，普通用户可折叠隐藏。
- **已绑定会话数量**（近似值或精确值）：依赖后端统计 API，可后续迭代。

#### 主操作

| 按钮 | 行为 |
|------|------|
| **保存** | `PATCH` Key 或专用子资源；成功 toast；失败展示后端错误信息（如校验失败、BYOK 无权）。 |
| **恢复默认** | 清空上游池并关闭开关（需二次确认），回到「仅默认 Chat 上游」行为。 |

### 7.3 与「默认 Chat 上游」卡片的关系

- **会话亲和关闭时：** 仍以现有 **默认 Chat 上游**（平台 / 单一 BYOK）为准，与当前产品一致。
- **会话亲和开启时：** 产品应明确 **默认 Chat 上游** 是否仍用于 **无会话键** 的退避路径；建议在详情页用一行 **灰色说明** 写清，避免两处冲突。推荐规则：**无会话键 → 仅用默认 Chat 上游，不参与 RR 池**（若采用 §2.3 方案 A）。

### 7.4 空态、加载与错误

| 场景 | 交互 |
|------|------|
| BYOK 列表加载失败 | 与现有关键详情一致：告警条，池内仅可选「平台上游」；修复后可刷新。 |
| 未配置服务端 BYOK 主密钥 | 禁用 BYOK 选项或整卡提示，与 `/byok-profiles` 行为一致。 |
| 保存冲突 | 展示服务端返回信息；建议乐观锁或「配置已被更新，请刷新」。 |

### 7.5 无障碍与国际化

- 上游池：每项有清晰 `aria-label`（如「上游 2：BYOK xxx」）；排序按钮带「向上移动」「向下移动」。
- 文案中间可保留英文 `Round Robin`、`X-Thread-Id`，需在中文语境下可读，或译为「顺序轮流分配」。
